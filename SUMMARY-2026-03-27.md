### Security — Ed25519 Sealed Envelope Handshake

Every cosmos-logos agent connection uses the same cryptographic handshake:

1. **Discovery** — Fetch `/.well-known/cosmos-logos.json` manifest from agent URL
2. **Health check** — Ping the agent's health endpoint
3. **Challenge generation** — Create a unique challenge string, compute its SHA-256 hash
4. **Key loading** — Load or generate client Ed25519 keypair
5. **Seal** — Encrypt the challenge using `crypto_box_seal` with the agent's Ed25519 public key (birational map to X25519)
6. **Sign** — Sign the request body with the client's Ed25519 private key
7. **Verify** — Send sealed envelope to agent's `/api/cosmos/verify-envelope` endpoint. Agent decrypts, hashes the challenge, returns `proof_hash`. Client verifies the hash matches.

This is implemented across 6 agent backends:
- **Node.js** (Athena, Apollo, Poseidon) — libsodium + `cryptokit-unseal.js` for Apple CryptoKit format
- **Python** (Thoth) — `cryptography` library with manual Ed25519→X25519 birational map
- **PHP** (Homework Buddy) — `sodium_crypto_scalarmult` + `openssl_decrypt`
- **Angular/Node** (Agora) — `cryptokit-unseal.js`
- **iOS** (TurtleShell iOS) — Pure Apple CryptoKit with Ed25519→X25519 birational map in Swift field arithmetic

## The Cosmos & Logos Question

### Context

Cosmos and Logos are the foundational agents — the first voices users hear. They are **free for everyone** (no Sea Shells subscription required). They represent TurtleShell's gift to the world.

- **Cosmos** navigates the agent constellation, routes conversations, explains what's possible
- **Logos** provides grounded wisdom, calms frustration, guides curiosity

### Current State

Cosmos and Logos currently exist as **built-in catalog entries** in the TurtleShell frontend. They have system prompts and voice configurations, but they are not yet standalone cosmos-logos services with their own backends. They don't have:

- A `/.well-known/cosmos-logos.json` manifest
- A `/api/cosmos/verify-envelope` endpoint
- An LLM backend to actually generate responses

### The Decision

We need to decide how Cosmos and Logos should work across the 3 modes:

**Option A: Lightweight agents backed by Ollama**
- Build small FastAPI or Express services (like Thoth)
- Point them at Ollama running a small model (Llama 3.2 3B, Phi-3 mini, Gemma 2B)
- Off-Grid: Ollama already runs in the Docker fleet on Mac Mini
- Developer: Ollama runs locally on the dev machine
- Cloud: Need to add Ollama to AWS (GPU instance) or use a serverless inference endpoint

**Option B: Agents backed by AWS Bedrock**
- Cloud mode uses Bedrock (Claude Haiku, Llama 3, etc.) — managed, scales automatically, pay-per-token
- Off-Grid: Still uses Ollama locally
- Developer: Uses Ollama locally or whatever the developer configures
- Pro: Zero GPU management on AWS. Con: Per-token cost (though very small for Haiku/Llama).

**Option C: Agents that route through Athena**
- Cosmos and Logos don't need their own LLM backend — they use Athena as the intelligence layer
- Their system prompt is injected into Athena's request
- Pro: No new infrastructure. Con: Depends on Athena being connected.

**Option D: Hybrid — Free tier uses a small local model, premium uses Athena**
- On Off-Grid and Developer: Ollama with a small model (free, fast, sovereign)
- On Cloud/Olympus-Grid: Route through Athena with a managed provider (Bedrock or direct API)
- This is arguably what already happens — the question is just what the "official" Cosmos/Logos cloud endpoints point at

### Key Considerations

1. **Launch day (7/17/2026)**: Cosmos and Logos must be available to everyone for free. They are the proof that TurtleShell works. If they're slow or down, first impressions are ruined.

2. **Cost**: Running GPU instances on AWS for Ollama is expensive (~$0.50-1/hr for a g5.xlarge). Bedrock pay-per-token is cheaper for low-to-moderate traffic. A small model on Bedrock (Claude Haiku, Llama 3 8B) costs fractions of a cent per conversation.

3. **Sovereignty message**: Cosmos and Logos running on a Mac Mini via Off-Grid is the purest expression of the mission. The official "cloud" version could literally be Gregory's Mac Mini behind a Tailscale/ngrok URL. That's authentic. That's the story.

4. **Scale**: If TurtleShell takes off on launch day, a single Mac Mini won't handle the load. Bedrock or a managed inference service would be the safety net.

5. **Model choice**: Cosmos and Logos don't need GPT-4 intelligence. They need personality, warmth, and fast responses. A 3B-8B parameter model with the right system prompt is more than sufficient.

### What We're Asking

Given this architecture — where every agent has Cloud, Developer, and Off-Grid modes — what is the best infrastructure strategy for Cosmos and Logos on launch day (7/17/2026)?

Specifically:
- What LLM backend should the **Cloud (Olympus-Grid)** version use?
- Should we add Ollama to the AWS infrastructure, use Bedrock, or route through Athena?
- What model size/family makes sense for agents that prioritize personality and availability over reasoning power?
- How do we keep it free while being prepared for scale?
